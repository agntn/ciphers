## Brute force

A Caesar has 25 keys. The attack is all of them, then read:

```bash
ciphers brute "KHOOR ZRUOG"
```

```
  shift= 3 → HELLO WORLD
  shift= 6 → EBIIL TLOIA
  shift=14 → WTAAD LDGAS
  ...
```

There is no dedicated function for this in the library, and there shouldn't be. It's `create("caesar").decode(text, { shift })` in a loop from 1 to 25 - that's what the command, the `ciphers_caesar_brute` tool and the [landing panel](/) run. Shift 0 isn't on the list. It would be the input, and the library refuses it as a shift anyway.

The command and `ciphers_caesar_brute` sort the same 25, the most English line first. With `--lang pl` on the command, or `lang: "pl"` on the tool, the most Polish one leads. `ja` does the same for Japanese romaji. A model then reads the answer on line one instead of wading to shift 17.

So how do you tell `HELLO WORLD` from `EBIIL TLOIA`? Not by letters. Both are made of common ones, and counted one by one the junk wins. English goes by letter pairs inside words instead, that's `pairFit`. `HE` is one English pair in 63, `II` one in 5800. On 10 characters of Pride and Prejudice or Frankenstein, pairs put the right shift first 92% of the time, single letters 72%. Polish and Japanese have no pair table yet, so they still rank by `fit`. A lone short word can still lose, and that's why all 25 come back.

The tool cuts them, though. Only its top line comes back whole, the rest stop at 80 characters with a `…`. Past that length and with the right `lang`, the ranking put the right shift first in all 6000 English and Polish samples I threw at it, and in 2000 Japanese ones. And 24 full copies of a 2000 character ciphertext are about 23 000 tokens of wrong answers. Eighty characters is plenty to see that a lower line reads. For the whole of it, decode with that shift. The command prints every line whole, a terminal has no context window to save.

## Frequency

```ts
import { analyzeFrequency } from "@agntn/ciphers";

const analysis = analyzeFrequency("DWWDFN DW GDZQ", "en");
analysis?.counts; // [["D", 4], ["W", 3], ["F", 1], ...] sorted by count
analysis?.reference; // "ETAOINSHRDLCUMWFGYPBVKJXQZ"
analysis?.ic; // index of coincidence
analysis?.referenceIc; // what plaintext in the language scores, 0.065 for English
analysis?.fit; // how much the letters look like English, higher is closer
analysis?.pairFit; // the same for letter pairs inside words, English only
```

`analyzeFrequency(text, language)` uppercases, drops everything outside A to Z and counts. No letters at all - `undefined`, not an empty table, so check before you read. The language picks the reference order, `en`, `pl` or `ja`. The English order is the Wikipedia letter frequency table. The Polish one is [PWN's count of the IPI PAN corpus](https://sjp.pwn.pl/poradnia/haslo/frekwencja-liter-w-polskich-tekstach;7072.html), base letters only, because the diacritics are gone before anything gets counted: `ż` counts for nothing, not for `z`.

Japanese is `ja`, romaji in Hepburn: `shi`, `chi`, `tsu`, `fu`, `ji`. I didn't find a published letter table for it, only keystroke counts from typing in the Kunrei style, where `C` and `J` never show up. So the table is built from the hiragana counts of [Chikamatsu et al. (2000)](https://doi.org/10.3758/BF03200819), a year of newspaper text. Each kana is spelled the way Japan's passport Hepburn table does it, `きょ` as `kyo`, and `っ` doubles the next consonant. L, Q, V and X get almost nothing instead of zero, so a loanword costs some fit but doesn't wipe it out. It only knows kana, not kanji readings. That's why it expects less `u`, `s` and `h` than real text has.

| Field | Meaning |
| --- | --- |
| `total` | Letters counted |
| `counts` | `[letter, count]` pairs, most frequent first |
| `reference` | Expected order for the language |
| `ic` | Index of coincidence, missing with fewer than two letters |
| `referenceIc` | Index of coincidence of plaintext in the language, from the same table as `reference` |
| `fit` | Mean log probability of one letter in the language. Closer to zero reads more like it |
| `pairFit` | Mean log probability of a letter pair inside a word, from [Norvig's counts](https://norvig.com/ngrams/). English only, missing when no word has two letters |

## Reading the index of coincidence

The IC is the chance that two letters picked from the text are the same. English sits near 0.065, Polish near 0.057 because its letters spread more evenly, uniform random near 0.038. Japanese romaji goes the other way. Five vowels carry about half the text, so it sits high: Kokoro and Rashomon measure 0.082, the kana table says 0.088. That one number tells you which family you are looking at before you try a single key:

- Monoalphabetic substitution (Caesar, Atbash, Affine) keeps the histogram shape and only relabels the bars. IC stays high, and the tallest ciphertext letter is probably E.
- Polyalphabetic (Vigenère, Alberti) spreads one plaintext letter over several ciphertext letters. IC drops toward 0.038 and the histogram goes flat. Time to look for a period.
- Transposition (rail fence, columnar) moves letters without changing them. The histogram is the plaintext's, only the words are gone.

The [Playground](/playground) draws the histogram for any text, expected order next to actual.

## The CLI

```bash
ciphers frequency "DWWDFN DW GDZQ"
ciphers frequency "ZAŻÓŁĆ GĘŚLĄ JAŹŃ" --lang pl
ciphers frequency "KIMIGAYO WA CHIYO NI" --lang ja
```

One bar per letter, expected and actual order, then the IC with the two reference values next to it so you don't have to remember them.

## Key length

The IC dropped to 0.038. Now what? A Vigenère key repeats, and that's the whole weakness. Take every fifth letter under a five-letter key and you're holding one Caesar. Get the length right and every column reads like plaintext again.

```bash
ciphers period "CHREEVOAHMAERATBIAXXWTNXBEEOPHBSBQMQEQERBWRVXUOAKXAOSXXWEAHBWGJMMQMNKGRFVGXWTRZXWIAKLXFPSKAUTEMNDCMGTSXMXBTUIADNGMGPSRELXNJELXVRVPRTULHDNQWTWDTYGBPHXTFALJHASVBFXNGLLCHRZBWELEKMSJIKNBHWRJGNMGJSGLXFEYPHAGNRBIEQJTAMRVLCRREMNDGLXRRIMGNSNRWCHRQHAEYEVTAQEBBIPEEWEVKAKOEWADREMXMTBHHCHRTKDNVRZCHRCLQOHPWQAIIWXNRMGWOIIFKEE"
```

```
  length  5  IoC 0.0666  key JANET
  length 10  IoC 0.0663  key JANETJANET
  length 15  IoC 0.0693  key JANETJANTTJANET
  length 20  IoC 0.0604
  length  3  IoC 0.0466
  ...
ℹ Kasiski: 12 trigram distances, most divided by 5 (10), 2 (4), 10 (4), 7 (3), 3 (2)
```

That's Example 1.11 from Stinson's Cryptography: Theory and Practice. The test suite checks it. Stinson gets the same column IoC by hand. Five, then decode:

```bash
ciphers decode vigenere "CHREEVOAHM..." --key JANET   # THEALMONDTREEWASINTENTATIVEBLOSSOM...
```

How does it know? For each length from 2 to 20, the letters get dealt into columns. Each column gets its IoC, the length gets their mean. Wrong length, every column mixes alphabets and sits near 0.038. Right length, it jumps to plaintext level. Here 0.047 at 3 against 0.067 at 5. Hard to miss.

Multiples are the trap. Ten columns under a five-letter key are still one alphabet each. They have fewer letters, so their IoC wobbles, often upward. Sort by IoC alone and 20 beats 5 on a short text. So a multiple goes right behind a divisor that reads almost as well. 5, then 10, 15, 20. I ran 300 random keys over README prose. At 200 letters the right length came first 90% of the time. At 400, every time. Plain IoC sorting managed 65%. Under 100 letters it's a coin toss either way.

Kasiski is the second opinion. It finds every trigram that repeats and measures the distance back to its last copy. Then it counts how many distances each factor divides. Why does that work? THE under the same key letters gives the same ciphertext. Those copies sit a multiple of the key length apart. Chance repeats add noise. And 2 always looks good, half of all numbers are even.

The top three lengths get a key. Each column takes the Caesar shift that reads most like the language. Same `fit` the brute force uses. `--lang pl` or `ja` changes the language, `--max-period` the longest length.

```ts
import { estimatePeriod } from "@agntn/ciphers";

const analysis = estimatePeriod(ciphertext, "en", 20);
analysis.periods[0]; // { period: 5, ic: 0.0666, key: "JANET" }
analysis.factors[0]; // { factor: 5, distances: 10 }
```

| Field | Meaning |
| --- | --- |
| `total` | A to Z letters, the ones Vigenère shifts |
| `periods` | `{ period, ic }` most likely first, `key` on the top three. Empty below four letters |
| `distances` | Distances between repeated trigrams |
| `factors` | `{ factor, distances }`, most distances first |
| `referenceIc` | IoC of plaintext in the language |

The key is Vigenère math. Beaufort has the same length but shifts the other way. Only the ranking helps there. Autokey has no length at all. Its key runs on into the plaintext and never repeats. Nothing to find, sorry.
