# ciphers/AGENTS.md

## Scope

Applies to the whole repository. A nested `AGENTS.md`, if introduced, overrides this file only for its subtree.

`@agntn/ciphers` provides local text transformations for educational, agent, and puzzle use. Nothing here is audited or meant for production, real funds or sensitive data, and the README and the first guide page say so. Other `@agntn` packages still build on these primitives rather than on `@noble/*` (keys takes AES for BIP38, #122). Cipher operations must not require HTTP, API keys, or another external service.

## Architecture

- Put each cipher in one `src/ciphers/<category>/<name>.ts` file. Its concrete class extends `Cipher`, implements `name()`, `info()`, `encode()`, and `decode()`, and is exported. A block cipher extends `BlockCipher` from `src/core/block-mode.ts` instead and implements `mode()` in place of `encode()` and `decode()`. Do not call `register()` from the file. A stream cipher extends `Cipher` and runs `encodeBlocks()` and `decodeBlocks()` with a `BlockMode` that has no `mode` and no padding, as `src/ciphers/stream/rabbit.ts` does.
- Modes of one block cipher share a folder instead: `src/ciphers/block/aes/` holds the AES primitive in `block.ts` and one file per mode, `ecb.ts` for `aes`, `cbc.ts` for `aes-cbc`, `cfb.ts` for `aes-cfb`, `ofb.ts` for `aes-ofb`, `ctr.ts` for `aes-ctr`, `ccm.ts` for `aes-ccm`, `ocb.ts` for `aes-ocb`, `lrw.ts` for `aes-lrw`, `xts.ts` for `aes-xts`, `cbc-mac.ts` for `aes-cbc-mac` and `passphrase.ts` for `aes-passphrase`. `src/ciphers/block/triple-des/` does the same for Triple DES: `block.ts`, `ecb.ts` for `triple-des` and `cbc.ts` for `triple-des-cbc`.
- Salsa20 and ChaCha get a folder each the same way: `src/ciphers/stream/salsa/` holds the rounds, HSalsa20 and the keystream in `block.ts`, then `salsa20.ts` and `xsalsa20.ts`. `src/ciphers/stream/chacha/` holds `block.ts` with HChaCha20, `poly1305.ts`, `chacha20.ts`, `xchacha20.ts` and `chacha20-poly1305.ts`. Both use the word helpers in `src/ciphers/stream/words.ts`, and the four plain streams read `nonce` and `counter` there.
- `rijndael` is not an AES mode, so it has its own `src/ciphers/block/rijndael.ts`. It runs the primitive from `aes/block.ts`, which takes the block length, and AES is that primitive at 16 bytes.
- `openpgp` runs several block ciphers, so it has its own folder, `src/ciphers/block/openpgp/`: `openpgp.ts` holds the cipher with its algorithm table and OpenPGP's CFB, `packets.ts` the packet framing, `armor.ts` the armor and its CRC-24, `s2k.ts` the string to key, `aead.ts` EAX, OCB and GCM and the chunks of AEAD data. ZIP, ZLIB and BZip2 come from the `deflate` and `bzip2` subpaths of `@agntn/compressions`, which import nothing from `node:`, so the docs still run the library in the browser. It takes the block functions `aesBlock`, `tripleDesBlock`, `cast5Block`, `blowfishBlock` and `ideaBlock` from their own files.
- `des` is not a Triple DES mode either, so it has its own `src/ciphers/block/des.ts` and runs `desBlock` from `triple-des/block.ts`, the same rounds Triple DES runs three times. `desx` runs that `desBlock` too, from its own `src/ciphers/block/desx.ts`.
- A category is one entry in `cipherCategories` in `src/core/ciphers.ts` and one folder under `src/ciphers/`. Every cipher reports it as `info().category`; `ciphers_info` and `ciphers ciphers` list by it and filter on it. Today there are `classical`, `block` and `stream`. A new kind of cipher gets its own category rather than a new `family` under one of them.
- Each category folder has an `index.ts` with its ordered list, and `src/ciphers/index.ts` concatenates those lists into `builtins`, the list the registry is seeded from. A cipher file that is not in them is not in the registry.
- `four-square` and `two-square` share their keyed squares, the `omit` and keyword checks, the pairs and the corner lookup in `src/ciphers/classical/squares.ts`; each cipher file keeps only how its squares are laid out.
- `quagmire-1` to `quagmire-4` share the tableau, the option checks and `info()` in `src/ciphers/classical/quagmire.ts`; each cipher file keeps only its number.
- Keep `src/core/registry.ts` constructor-based. `create()` returns one cached instance per name, and re-registering a name invalidates that instance.
- Byte functions of a cipher family go in their own subpath entry, `src/<family>.ts` in `build.config.ts` and `./<family>` in `exports`, not in the root barrel. `src/aes.ts` imports only the AES files and the errors, so a consumer of `@agntn/ciphers/aes` bundles no registry and no other cipher. `src/chacha.ts` (`./chacha`) and `src/salsa.ts` (`./salsa`) do the same for their families.
- `sideEffects` names `dist/cli.mjs` and nothing else. That holds only while no module registers itself on import: put a `register()` call back at the top of a cipher file and the class reaches the registry through a bare import, which a tree-shaker is free to drop. New ciphers go in `builtins`.
- `src/cli.ts` is `runCli` from `@agntn/tools/cli` over `ciphersTools`, with `mcp: serverInfo` from `src/server-info.ts`, so the bundled server shows the same description and icons as the remote one. The `cli` hint on each tool in `src/tools.ts` keeps the old command names (`brute`, `period`, `guess`, `probe`, `crib`, `hidden`, `recover`, and `ciphers` as an alias of `info`), its positionals, `-` on stdin for the text and for `book`, and a short line for the command list. `default: 'info'` lists the ciphers on an empty line and `fallback: 'encode'` reads a first word that names no command as a cipher. Flags are the schema's property names in kebab case, arrays come in as JSON (`crib`, the `probe` grids), and `CipherError` prints as one line with exit code 1. No tool declares short flags. `@agntn/tools` 0.2.1 reads a dashed word that spells no flag as the next free positional, so Morse and armor need no `--`, and once the positionals are full a dashed word is an unknown option again.
- `test/unit/cli-loads.test.ts` runs the usage paths under a load hook: `--help` loads neither the MCP SDK nor `src/mcp.ts` nor the cipher library.
- Inside a checkout, a bare `mcp` from the built `dist/cli.mjs` skips `runCli` and serves `createMcpServer` from `src/mcp.ts`, like the Pi and OMP extensions, so a local server needs only a restart after a change. The npm package ships no `src/` and runs the `mcp` of `runCli`, and so does a copy under `node_modules`, where Node does not strip types. A checkout without devDependencies still runs the source, since the server imports production dependencies only. `CIPHERS_DIST=1` forces the bundle. A change to `src/cli.ts` itself still needs `pnpm build`; `test/eval-packed.mjs` runs `mcp` in each of these layouts.
- The sources run under plain Node: relative imports name the `.ts` file (or `index.ts` for a folder), and there are no `enum`, `namespace` or parameter properties. `tsconfig.json` holds that with `NodeNext`, `allowImportingTsExtensions` and `erasableSyntaxOnly`.
- Report domain failures through the `CipherError` hierarchy and normalize unknown thrown values with `normalizeError()`.
- Resolution may normalize case and spaces to hyphens, then it must match a registered name exactly. Do not add fuzzy or prefix matching.
- Keep the `ciphers` CLI and the Pi/OMP extensions aligned with the library. Both extensions expose encode, decode, Caesar brute force, frequency analysis, key length estimate, family guess, passphrase probe, crib dragging, hidden text reading, key recovery, and cipher info lookup.
- Each agent tool is one `defineTool` in `src/tools.ts`, from `@agntn/tools`. `src/mcp.ts` serves that list with `createMcpServer` from `@agntn/tools/mcp` under `serverInfo` from `src/server-info.ts`, the name, version, description and icons the remote server shows too, and its `toolListings` and `callTool()` run the remote server at `ciphers.agntn.dev/mcp`, where a new tool also needs a file in `docs/server/mcp/tools/` (see `docs/AGENTS.md`). The extensions register the same list with `registerPiTools` and `registerOmpTools`, from `src/tools.ts` in a checkout and `dist/tools.mjs` in the package. Build schemas with `Type` from `@agntn/tools`, never from a bare `typebox` import, which OMP rewrites to its own facade.
- The core checks every call against the schema on every surface, and an argument the tool does not take is refused. What the schema cannot say per cipher (which ciphers need `key`, `iv`, `nonce` or `period`, and their hex key lengths) is `cipherInputError` in `src/tools.ts`. The executors stay in `src/tool-operations.ts`, which the docs run too, and the library loads on the first call.
- OMP lists the tools as `discoverable`, its default for extension tools, because `registerOmpTools` takes no `loadMode` yet (agntn/tools#8).

## Cipher Contracts

- Latin cipher alphabets use A-Z.
- Playfair and Polybius map J to I.
- `four-square` takes `key` and `secondKey`, the keywords for the keyed squares at the top right and the bottom left, each built as Playfair builds its table, and reads each pair across the corners of two plain squares, as Practical Cryptography does. `omit` picks the letter the squares leave out: `j` (default) folds J into I, `q` drops Q from the squares, the keywords and the text and keeps J, as the English Wikipedia page does. The result options carry `omit` only when it is `q`. The text loses everything but A-Z and comes out in capitals; `X` pads an odd length and nothing splits a doubled pair. Decoding keeps the `X` and throws `CipherError` on an odd number of letters. Its family is `digraph`. `guessFamily` names it for an even count with no J, right after bifid and as sure as bifid when a pair doubles (as sure as Playfair would be under the 40 letters bifid needs), one step lower after Playfair when none does. It doesn't name the Q-less squares, whose ciphertext keeps J. The fixed vectors are the ATTACK AT DAWN example and the pycipher example on Practical Cryptography, and the EXAMPLE and KEYWORD example on the English Wikipedia page for `omit: q`.
- `two-square` takes `key` and `secondKey`, the keywords for its two keyed squares, built as for `four-square`, with the same `omit`. `orientation: vertical` (default) stacks them, `key` on top: each letter comes back from its own square on its own row in the other letter's column, so a pair in one column stays as it was, as the English Wikipedia page shows, and decoding is the same step. `orientation: horizontal` sets `key` on the left: the result's first letter comes from the right square, so a pair in one row comes out reversed, as the ACA and dCode do, and decoding looks the pair up with the squares swapped. Crypto Corner trades rows instead, so its horizontal ciphertext differs. The result options carry `orientation` only when it is `horizontal` and `omit` only when it is `q`. Text, padding and errors work as for `four-square`. Its family is `digraph`. `guessFamily` names it next to four-square: one step lower after it, or as sure and ahead of it when the pairs at even positions score above `-0.6 / √letters` on `transparentPairScore` from `src/core/frequency.ts`, straight for vertical or reversed for horizontal. That catches about half of 100-letter two-square texts and seven in ten at 400, and puts it ahead of about one four-square in eight; only English has the pair table. The fixed vectors are the EXAMPLE and KEYWORD example on the English Wikipedia page for `omit: q`, the same keywords on Crypto Corner for the default, the DIALOGUE and BIOGRAPHY example in the ACA's TwoSquare.pdf and the KEY and WORD example on dCode for `horizontal`.
- `hill` takes `key` as 4 or 9 letters, a 2×2 or 3×3 matrix row by row with A as 0, and multiplies each block of letters as a column vector, as the English Wikipedia page does. A key whose determinant shares a factor with 26 is an `InvalidOptionError` before the first letter, both ways. The text loses everything but A-Z and comes out in capitals; `X` pads a short last block, and decoding keeps it and throws `CipherError` on letters that don't split into whole blocks. Its family is `polygraphic`. `guessFamily` names it, at most `medium`, for letters only in whole blocks of 2 or 3, flat counts and a J. The fixed vectors are the `DDCF` and `GYBNQKURP` examples on the English Wikipedia page.
- `nihilist` takes `key`, the additive keyword, and `square`, an optional keyword for the 5×5 square that Polybius builds, J as I in both. Each letter becomes its row and column digits and the key letter under it, repeating, adds its own, as plain numbers: no wrap, so 106 stays 106. Encoding drops what is not A-Z and joins the numbers with single spaces. Decoding reads every run of digits and throws `CipherError` on a number the key can't take back to a cell from 11 to 55, or on text with no number at all. Its family is `fractionation`. `guessFamily` names it, at most `medium`, for numbers from 22 to 110 with none ending in 1. The fixed vector is the ZEBRAS and RUSSIAN example on the English Wikipedia page.
- `substitution` takes `key` as a whole cipher alphabet, exactly 26 cells of A-Z and `?` for plaintext A to Z with no letter twice, or as a keyword whose letters come first, repeats dropped, before the rest of A-Z. A `?` cell in a whole alphabet is a letter left unknown, the way `recoverKey` writes it: it encodes and decodes to `?`. A `?` anywhere else is an `InvalidOptionError`. The fixed vector is the ZEBRAS example on the English Wikipedia page.
- `gronsfeld` takes `key` as a string of ASCII digits and nothing else, so a leading zero stays a shift: digit d shifts one letter d places, as Vigenère key letter d after A does, and the key repeats. Only ASCII letters advance it and the rest passes. A number, a space or any other character in the key is an `InvalidOptionError`. Its family is `polyalphabetic`, and `guessFamily` lists it with the other polyalphabetic ciphers. `recoverKey` takes it as `vigenere`, a key of A to J. The fixed vectors are the GRONSFELD and DCODE examples on dCode and `0123` as Vigenère `ABCD` from the English Wikipedia page.
- `running-key` takes `key` as a passage and adds its letters to the text as Vigenère does, one key letter per text letter and never round again. Only ASCII letters count on both sides and the rest passes. A key with fewer letters than the text is an `InvalidOptionError` with both counts, and a key with none is one too; the error and the result options name the passage by its counts, never quote it. Letters past the text stay unused, and the result options carry `keyUsed`, the letters the text took. Its family is `polyalphabetic`, and `guessFamily` lists it with the other polyalphabetic ciphers. `recoverKey` takes no running key. The fixed vector is the K&R example on the English Wikipedia page.
- `porta` takes `key` and runs the 13 reciprocal tables the ACA prints: key letters pair up as A and B, C and D, up to Y and Z, each table swaps A-M with N-Z, and the N-Z half turns one place left per table. `rotation: right` turns it right instead, dCode's default table. Only ASCII letters advance the key and the rest passes. Its family is `polyalphabetic`, and `guessFamily` lists it with the other polyalphabetic ciphers. The fixed vectors are the FORTIFICATION example and the tableau on Practical Cryptography, and the DCODE and PORTA example on dCode.
- `quagmire-1` to `quagmire-4` run the ACA's Quagmires: one tableau, a plain alphabet on top and a cipher alphabet that slides under it. A keyed alphabet is the keyword's letters, repeats dropped, then the rest of A-Z. `key` keys the plain alphabet for I, the cipher alphabet for II and both for III; IV keys the plain one with `key` and the cipher one with `secondKey`, which the other three ignore. `indicator` is required: each of its letters in turn slides the cipher alphabet until that letter stands under `indicatorUnder` (one letter, default A) on the plain alphabet, and that row takes one letter of the text. Only ASCII letters advance it and the rest passes; the keywords drop what is not a letter. Their family is `polyalphabetic`, and `guessFamily` lists them with the other polyalphabetic ciphers. `recoverKey` takes none of them. The fixed vectors are the ACA's example for each type, Quagmire IV with its indicator under S.
- Tap code shares C and K.
- `a1z26` numbers A-Z from 1 to 26 and joins the numbers of one word with `separator` (default `-`, at most 10 code points); everything that is not a letter passes. Decoding drops the separator only between two numbers and throws `CipherError` on a number outside 1 to 26. `zero`, one letter from J to Z, switches to the single digit form: A to I for 1 to 9 and that letter for 0, encoding digits and decoding letters in either case, and it takes no `separator`. The fixed vectors are the two dCode examples and `bef` as `256` from issue #160.
- `book` counts in the text `book`. A word is letters and digits in any script with their combining marks: an apostrophe inside keeps it one word, anything else splits it. A line without a word is not counted, and a form feed starts a page. `address` is `word` (default), `line-word` or `page-line-word`, `pick` the whole `word` (default) or its first `letter` in NFC, and `start` 1 (default) or 0. Encoding drops what is not a word, or a letter or digit with `pick: letter`, matching words in NFC with case folded (`SS`, `ẞ` and `ß`, both Turkish I and `i`), and gives a repeated one the next matching word, wrapping round. Decoding reads every number in order, as many per address as `address` takes, gives one letter per address in capitals unless the capital is longer (`ß` stays `ß`), and throws `CipherError` on a number out of range or an incomplete address. The result options carry the counts of words, lines and pages, never the book. Its family is `homophonic`, since a letter can take any word that starts with it. The fixed vectors are the two dCode examples over the National Archives transcription of the Declaration of Independence and word 115 as `instituted` from the Wikipedia page on the Beale ciphers.
- Morse uses dots and dashes, spaces between letters, and `/` between words.
- Bacon defaults to the 26-letter A-Z variant; `letters: 24` selects the historical table with I/J and U/V shared. Decoding throws `CipherError` when the A and B in the text don't split into groups of five, or when there are none.
- ADFGVX runs its columnar transposition only when `transposition` is set; without it the output is the grid step alone. Decoding throws `CipherError` when the A, D, F, G, V and X in the text don't split into pairs, or when there are none.
- `straddling-checkerboard` takes `key` as the whole board, 28 cells row by row with each letter A-Z once and two fillers that may repeat, and `blanks` as the two blank digits of the top row, in the order of their rows. The default is the English Wikipedia board `ETAONRISBCDFGHJKLMPQ/UVWXYZ.` with blanks `26`. Encoding drops what is not on the board, a repeated filler encodes as its first cell, and `/` is a plain cell, not a numeral escape. Decoding reads digits only and throws `CipherError` when there are none or the last one is a blank. The fixed vectors are the Wikipedia example and its second table, and GSMG.IO phase 3.2.2 from the puzzle's public writeup.
- `route` fills a grid of `width` cells per row and walks it from `corner` (default `top-left`) along `path`: `spiral-clockwise` (default), `spiral-counterclockwise`, `snake-rows`, `snake-columns` or `columns`. Decoding reads the path off the rows, as a puzzle grid is solved, which is the reverse of Wikipedia and dCode, where encryption reads the path. Every character but a line break is a cell, and a short last row leaves empty cells every path skips. The fixed vectors are the Wikipedia route cipher example and the GSMG.IO opening grid.
- Enigma models Wehrmacht M3 with rotors I-II-III and reflector B.
- Every block and stream cipher, `aes-passphrase` and `openpgp` included, takes `bytes`: `text` (default) reads and writes the plain side as UTF-8, `hex` as hex with no UTF-8 check. `decodeBlocks` owns it, and its not-UTF-8 error names `bytes: hex` for every cipher. The result options carry `bytes` only when it is `hex`, except for `xor`, which reports it always.
- `aes` runs in ECB only: UTF-8 text with PKCS#7 padding in, lowercase hex out, and a key of 32, 48 or 64 hex digits. It is a teaching implementation, not constant time. `ecb` from the `@agntn/ciphers/aes` subpath (`src/aes.ts`) runs the same ECB on a `Uint8Array`: whole blocks in and out, no padding and no hex, and a key of 16, 24 or 32 bytes.
- AES-CBC takes the AES key and a required 32-digit `iv`, and chains blocks as NIST SP 800-38A §6.2 does. Text, padding and hex work as for AES.
- AES-CFB takes the AES key and a required 32-digit `iv`, and feeds back `segment` bits per step (1, 8 or 128, default 128) as NIST SP 800-38A §6.3 does. It has no padding: the ciphertext has as many bytes as the UTF-8 text. Hex works as for AES.
- AES-OFB takes the AES key and a required 32-digit `iv`, and encrypts each output block again for the next, starting from the IV, as NIST SP 800-38A §6.4 does. Padding and hex work as for AES-CFB.
- AES-CTR takes the AES key and a required 32-digit `iv`, the initial counter block, and adds one to it per block as a 128-bit big-endian number, wrapping to zero, as NIST SP 800-38A §6.5 and §B.1 do. Padding and hex work as for AES-CFB. `ctr` from the `@agntn/ciphers/aes` subpath runs the same CTR on a `Uint8Array` of any length, with a key of 16, 24 or 32 bytes and a 16-byte `counter`.
- AES-CCM takes the AES key, a required `nonce` of 14 to 26 hex digits, optional hex `aad` and `tagLength` in bits (32 to 128 in steps of 16, default 128), and runs NIST SP 800-38C: CBC-MAC for the tag, CTR for the text and the tag. The output is the ciphertext followed by the tag in hex, with no padding. Decoding throws `CipherError` and returns no text when the tag does not match.
- AES-OCB takes the AES key, a required `nonce` of 2 to 30 hex digits, optional hex `aad` and `tagLength` in bits (64, 96 or 128, default 128), and runs RFC 7253. Output, padding and a tag that does not match work as for AES-CCM.
- AES-LRW takes the AES key followed by a 32-digit tweak key, masks block `i` with `K2 ⊗ i` in GF(2^128) as IEEE P1619 LRW does, and counts `i` up from `tweak` (hex, default 1). Text, padding and hex work as for AES.
- AES-XTS takes two AES-128 or two AES-256 keys in one key of 64 or 128 hex digits, the data key then the tweak key, and runs IEEE 1619 with `tweak` as the data unit number (hex, default 0, little-endian in the tweak block as OpenSSL takes its IV). A short last block uses ciphertext stealing, so there is no padding, the text must be at least 16 bytes, and one data unit is at most 2^20 blocks as NIST SP 800-38E requires. Equal key halves are accepted, as in IEEE vector 1. Hex works as for AES-CFB.
- AES-CBC-MAC takes the AES key only and runs FIPS 113, ISO/IEC 9797-1 MAC Algorithm 1: CBC with a zero IV over the text padded with zeros to whole blocks (one zero block when empty), the last block as a 16-byte tag. Nothing is encrypted. The output is the UTF-8 bytes followed by the tag in hex, and a tag that does not match works as for AES-CCM.
- `aes-passphrase` reads and writes what `CryptoJS.AES.encrypt(message, passphrase)` gives: base64 of `Salted__`, an 8-byte salt and AES-CBC with PKCS#7. The key is the passphrase as UTF-8 text, and key and IV come from it and the salt through OpenSSL's `EVP_BytesToKey`, which CryptoJS calls EvpKDF, over the hash `digest` names: `md5` (default), `sha1` or `sha256`, the last being `openssl enc` since 1.1.0. Both come from `@agntn/hashes`. `keyLength` (bits, 128 to 1024 in steps of 32, default 256) is CryptoJS `keySize` times 32, and past 256 bits the Rijndael key schedule runs `keyLength / 32 + 6` rounds as CryptoJS does. `iterations` (1 to 100000, default 1) is EvpKDF's. `salt` (16 hex digits) fixes the salt when encoding, random otherwise. The fixed vectors are crypto-js 4.2.0, `openssl enc -md md5` for 128 and 256 bits, and `openssl enc` 3.6 with `-md sha1` and `-md sha256`.
- `probePassphrase` (`ciphers probe`, `ciphers_passphrase_probe`) tries one passphrase on an `aes-passphrase` blob under every digest, key length and iteration count of a grid, md5, sha1 and sha256 at 128, 192 and 256 bits and one iteration by default. It runs `EVP_BytesToKey` once per digest and iteration count and decrypts the last block only until the padding holds. Hits come most printable first, next to the hits a wrong passphrase gives by chance, tries times `(1 - 256^-16) / 255`. The iteration counts add up to at most 1000000 hash passes across the digests.
- `recoverKey` (`ciphers recover`, `ciphers_key_recover`) searches the key of `vigenere`, `beaufort`, `variant-beaufort` (plaintext is ciphertext plus key, so `vigenere` encode reads it), a monoalphabetic `substitution` or `columnar`, and returns up to 20 keys, best first, each with its plaintext. English is scored by the 16,000 commonest quadgrams of ten Project Gutenberg books in `src/core/quadgrams.ts`, counted with spaces dropped, since counts inside words can't score a text without spaces; a missing quadgram backs off to its letter frequencies. Polish and Japanese romaji are scored by single letters, so only the periodic ciphers take them, and a key pays ln 26 per letter there. Periodic keys come from chi-squared per column over the five likeliest lengths, then single and neighbouring pair changes; substitution climbs over letter swaps from the frequency order and seeded random starts, so a text always gives the same keys; columnar tries every order of 2 to 8 columns, or of `keyLength` up to 9. The fixed vectors are Stinson's Example 1.11 and texts outside the corpus encoded with known keys.
- `rijndael` runs in ECB only, with `blockSize` in bits (128, 160, 192, 224 or 256, default 128) and a key of 32, 40, 48, 56 or 64 hex digits, as the Rijndael proposal allows. A 128-bit block is AES. Text, padding and hex work as for AES, with blocks of `blockSize`.
- `des` runs in ECB only, as FIPS 46-3 single DES with a key of 16 hex digits. Parity bits are ignored and weak keys are accepted. Text, padding and hex work as for AES, with 8-byte blocks.
- `desx` runs in ECB only, as Rivest's DESX: each block is XORed with an input whitening key, encrypted by `des` and XORed with an output whitening key. The key is 48 hex digits in OpenSSL's `desx-cbc` order, the DES key, then the input and the output whitening key; Botan and the Polish Wikipedia put the input key first. Text, padding and hex work as for `des`.
- `triple-des` runs in ECB only, as EDE with a key of 32 hex digits (K3 = K1) or 48 (three keys). Parity bits are ignored. Text, padding and hex work as for AES, with 8-byte blocks.
- Triple DES CBC takes the Triple DES key and a required 16-digit `iv`, and chains blocks as NIST SP 800-38A §6.2 does. Text, padding and hex work as for Triple DES.
- `blowfish` runs in ECB only, with a key of 8 to 112 hex digits (4 to 56 bytes, the 32 to 448 bits of Schneier's paper). The P-array and S-boxes start from the fractional hex digits of pi, computed once in `BigInt` rather than stored. Text, padding and hex work as for Triple DES.
- `idea` runs in ECB only, as Lai and Massey's IDEA with a key of 32 hex digits: 8.5 rounds on 16-bit words, with the word 0 standing for 2^16 in multiplication modulo 2^16 + 1. Its family is `lai-massey`, since it is neither Feistel nor SPN. Text, padding and hex work as for Triple DES.
- `lucifer` runs in ECB only, as Sorkin's Lucifer from Cryptologia 8(1), 1984, with his bit numbering correction from Cryptologia 8(3), July 1984 applied: 16 Feistel rounds on 16-byte blocks and a key of 32 hex digits. The uncorrected January listing, and code copied from it, gives other ciphertext; the fixed vectors are Outerbridge's 2015 triples. Text, padding and hex work as for AES.
- `mars` runs in ECB only, as IBM's MARS with the key schedule tweak of August 1999: 32 rounds on four little-endian 32-bit words and a key of 32 to 112 hex digits in steps of 8 (4 to 14 words). The 512-word S-box is built once from SHA-1 as section 2.6 of the submission describes, not stored. The fixed vectors are IBM's known answers from Crypto++, plus CycloneCRYPTO for the 160 and 416-bit keys Crypto++ refuses. Text, padding and hex work as for AES.
- `serpent` runs in ECB only, as Anderson, Biham and Knudsen's Serpent: 32 rounds of eight 4-bit S-boxes applied in bitslice mode on four little-endian 32-bit words, and a key of 32, 48 or 64 hex digits. The byte order is libgcrypt's and Botan's; code that reverses the bytes gives other ciphertext. The fixed vectors are Botan's `serpent.vec`, all 960 single-bit ones by digest, and whole texts come from libgcrypt. Text, padding and hex work as for AES.
- `cast5` runs in ECB only, as CAST-128 from RFC 2144 with a key of 10 to 32 hex digits in whole bytes (40 to 128 bits): a shorter key is padded with zeros to 16 bytes, and a key of 80 bits or less runs 12 rounds instead of 16. The eight S-boxes are stored as Appendix A prints them, since nothing generates them. The fixed vectors are RFC 2144 B.1 for the 128, 80 and 40-bit keys and `openssl enc -cast5-ecb` for UTF-8 text; the B.2 maintenance test takes about 20 seconds and runs outside the suite. Text, padding and hex work as for Triple DES.
- `openpgp` reads and writes a passphrase-protected OpenPGP message, RFC 4880: what `gpg --symmetric` writes. Decoding takes armor, or the bare packets in base64 or hex, tries at most 8 SKESK packets with S2K type 0, 1 or 3 over MD5, SHA-1, RIPEMD-160, SHA-224, SHA-256, SHA-384, SHA-512, SHA3-256 or SHA3-512, and opens the data they go with. A v4 packet (an encrypted session key included) opens SEIPD v1 with IDEA, Triple DES, CAST5, Blowfish or AES in OpenPGP's CFB with a zero IV; the repeated prefix bytes tell a wrong passphrase, the MDC a changed message. A v5 packet opens AEAD encrypted data (tag 20) as GnuPG writes it, and a v6 packet SEIPD v2 of RFC 9580, both with AES in EAX, OCB or GCM: the tag on the sealed session key tells a wrong passphrase, a chunk tag or the final tag over the length a changed or cut message. Either way it throws `CipherError` with no text, and an AEAD message reports its mode as `aead` and no `iv`. Inside, ZIP, ZLIB and BZip2 decompress to at most 4 MiB, 4 levels deep, signature packets are skipped unchecked, and text mode turns CRLF into LF as `gpg --decrypt` does. Twofish, Camellia, SED packets and Argon2 each throw a `CipherError` that names them; a passphrase packet in one of those is skipped while another can still open the message. Encoding writes armor GnuPG opens: SKESK v4 with an iterated and salted S2K, SEIPD v1 over a binary literal packet with no file name and a zero date, no compression, with `algorithm` (default `aes256`), `digest` (default `sha512`, as GnuPG 2.4) and `count` (1024 to 65011712, rounded up to the coded count, default the maximum). `salt` and `iv`, the random first block, fix the random values, and the result options of `decode` give back the same armor for a message `encode` wrote. The fixed vectors are GnuPG 2.4.9 messages for every algorithm, S2K type, hash and compression above and the message from issue #165; GnuPG writes no SHA-3, so the SHA3-256 and SHA3-512 messages come from OpenPGP.js 6.3.2. GnuPG writes OCB as its only AEAD mode, so EAX and GCM come from the samples of RFC 9580 A.9 to A.11, rfc4880bis-10 A.3 and LibrePGP A.3, OCB from those and from GnuPG.
- `rabbit` runs RFC 4503 with a key of 32 hex digits and an optional `iv` of 16; without it the IV setup is skipped. `endian` picks the byte order of key, IV and keystream: `big`, the default, reads them most significant byte first as the RFC's test vectors and CyberChef do, `little` as the eSTREAM reference code, Crypto++, wolfSSL and libtomcrypt do. A short last block takes the least significant keystream bytes, as §2.8 says, so the last bytes of the block under `big`. No padding, and hex works as for AES-CFB. The fixed vectors are Appendix A of RFC 4503, Crypto++ 8.9 for `little`, and CyberChef's short block.
- `rc4` runs Rivest's RC4 with a key of 2 to 512 hex digits in whole bytes (1 to 256 bytes) and no IV, and drops nothing from the start of the keystream. Its family is `permutation`, since its state is one shuffled table of all 256 byte values. No padding, and hex works as for AES-CFB. The fixed vectors are RFC 6229 section 2, the three on the English Wikipedia page, and `openssl enc -rc4` for UTF-8 text.
- `salsa20` runs Bernstein's Salsa20/20 with a key of 32 or 64 hex digits (a 128-bit key fills both key rows under `expand 16-byte k`), a required `nonce` of 16 and an optional `counter`, the first 64-byte block, from 0 to 2^53 - 1 (default 0), since the 64-bit counter goes through a JavaScript number. `xsalsa20` takes a key of 64 and a `nonce` of 48: HSalsa20 over the key and the first 16 nonce bytes gives the subkey, and Salsa20 runs under it with the last 8. No padding, and hex works as for AES-CFB. The fixed vectors are eSTREAM set 1 vector 0 and set 3 vector 243, the Crypto++ vector across the 32-bit counter boundary, and two Crypto++ XSalsa20 vectors from naclcrypto-20090308.
- `chacha20` runs RFC 8439 with a key of 64 hex digits, a required `nonce` of 24 and a `counter` from 0 to 2^32 - 1 (default 0, where the RFC's examples start at 1). A text that needs a block past 2^32 - 1 is an `InvalidOptionError`, not a wrap. `xchacha20` runs draft-irtf-cfrg-xchacha: HChaCha20 over the key and the first 16 bytes of a 48-digit `nonce`, then ChaCha20 under that subkey with four zero bytes and the last 8. No padding, and hex works as for AES-CFB. The fixed vectors are RFC 8439 §2.3.2, §2.4.2 and A.2 #1 and #3, and the draft's §2.2.1 and A.2.1 and A.2.2.
- `chacha20-poly1305` runs AEAD_CHACHA20_POLY1305 of RFC 8439 §2.8 with the ChaCha20 key and `nonce` and optional hex `aad`, and has no `counter`: block 0 gives the Poly1305 key and the text starts at block 1. The output is the ciphertext followed by a 16-byte tag, and a tag that does not match works as for AES-CCM. Poly1305 runs in `BigInt`. The fixed vectors are RFC 8439 §2.5.2, A.3 #5 to #11, §2.8.2 and A.5. `chacha20`, `xchacha20` and `chacha20Poly1305` from `@agntn/ciphers/chacha`, and `salsa20` and `xsalsa20` from `@agntn/ciphers/salsa`, run the same on a `Uint8Array`.
- `xor` runs repeating-key XOR: key byte `i mod length` XORed into byte `i`, with a key of any nonzero even number of hex digits and no upper limit in the library. Its family is `polyalphabetic`, since it is Vigenère on bytes. Text, padding and hex work as for `rc4`. The fixed vector is Cryptopals set 1 challenge 5.

## Adding or Changing a Cipher

1. Add or update the cipher class and its option types.
2. For a new cipher, export the class, add it to its category list in `src/ciphers/<category>/index.ts`, and add its name to `builtinCiphers` in `src/core/ciphers.ts` in the same position `builtins` gives it. A new category also needs its entry in `cipherCategories` and its list spread into `builtins`.
3. Run a roundtrip probe before writing fixtures.
4. Add an independently known fixed vector plus relevant edge cases to `test/unit/ciphers.test.ts`. Never manufacture the expected value from the implementation under test.
5. Update the tool definitions in `src/tools.ts` (the CLI is built from them), exports, and README only where the public contract changed.

Use the scripts in `package.json` as the command source of truth. A cipher change is complete when its focused tests pass and every affected public surface builds and typechecks.
