---
title: AES (CBC)
description: AES with the blocks chained. Every 16-byte block is mixed with the ciphertext before it, so equal blocks stop looking equal. UTF-8 text in, hex out.
---

::cipher-facts{name="aes-cbc"}
::

CBC is cipher block chaining, the mode from NIST SP 800-38A that most CTFs with AES end up using. It's [AES](/ciphers/aes) with one step before every block. The plaintext block is XORed with the ciphertext block that came out just before it, then encrypted. The first block has nothing before it, so it gets the IV instead. Decryption runs it backwards: decrypt the block, then XOR with the previous ciphertext block, or with the IV for the first one.

The key is 32, 48 or 64 hex digits, same as in ECB. `iv` is 32 hex digits, one block, and it's required. There's no default, because a silent all-zero IV is exactly the kind of thing that gives you the wrong plaintext with a straight face. Text and ciphertext work as in AES: UTF-8 with PKCS#7 padding in, lowercase hex out, and `decode` wants hex back.

```ts
const cbc = create("aes-cbc");
const key = "2b7e151628aed2a6abf7158809cf4f3c";
const iv = "000102030405060708090a0b0c0d0e0f";
cbc.encode("ATTACK AT DAWN", { key, iv }).text; // "9bae05a967f1cf1d7d3601f7ef8b4d79"
cbc.decode("9bae05a967f1cf1d7d3601f7ef8b4d79", { key, iv }).text; // "ATTACK AT DAWN"
```

OpenSSL gives the same bytes:

```bash
printf %s "ATTACK AT DAWN" | openssl enc -aes-128-cbc -K 2b7e151628aed2a6abf7158809cf4f3c -iv 000102030405060708090a0b0c0d0e0f | xxd -p
```

The block function is tested against the CBC-AES128, 192 and 256 vectors from NIST SP 800-38A, F.2.

## What the chain fixes

Thirty-two `A`s, two equal blocks of plaintext. In ECB they come out as two equal blocks of ciphertext. Here:

```ts
cbc.encode("A".repeat(32), { key, iv }).text;
// ab74350f2f19b4ea4de050762e12dbc1 8d2f731d5ae2fa0858814a0e6df219ca 25292ca5cf9e35a0afb9452d5c640c6e
```

Spaces added here to show the blocks. Nothing repeats, because the second block was mixed with the first one's ciphertext before AES saw it. But the same message under the same key and the same IV gives the same ciphertext again. That's why the IV should be new for every message.

## What it doesn't fix

On decryption the previous ciphertext block, or the IV, is XORed in after AES. So whoever can change it changes the plaintext, bit for bit, without the key. Flip bytes in the IV and the first block says what you want:

```ts
cbc.decode("9bae05a967f1cf1d7d3601f7ef8b4d79", { key, iv: "000102030405060708090a1f08080e0f" }).text;
// "ATTACK AT DUSK"
```

That IV is the old one XORed with `DAWN` and `DUSK` at bytes 10 to 13. Nobody touched the key. Flip a byte in a ciphertext block instead and that block decrypts to garbage, while the next one gets the same flip. It's the bit flipping attack from every other CTF, and with an error that tells bad padding apart, it's also the padding oracle.

A key that isn't 32, 48 or 64 hex digits is an `InvalidOptionError`, and so is an `iv` that isn't 32 hex digits. A missing key or IV is a `MissingOptionError`. On `decode`, hex that isn't whole 16-byte blocks is a `CipherError`. So is a wrong key, since the padding almost never survives it. A wrong IV garbles only the first block. In a one-block message that breaks the padding, in a longer one it's almost always bytes that aren't UTF-8. But an IV that's only a little off, like the one above, decodes without a word.

No integrity check, plain TypeScript, not constant time. For puzzles and for seeing what the chain does. Don't protect anything real with it.
